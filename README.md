## Реализация

Приложение предоставляет REST API для управления данными фитнес-клуба. API позволяет выполнять CRUD-операции с клиентами, тренерами, специализациями, залами и персональными тренировками, а также получать результаты аналитических запросов.

Данные на данном этапе хранятся в коллекциях в памяти. Для организации приложения используется слоистая архитектура, разделяющая предметную область, контракты, бизнес-логику, инфраструктуру хранения данных и HTTP API.

Запуск и оркестрация приложения выполняются с помощью .NET Aspire через проект `FitnessClub.AppHost`.

База данных PostgreSQL и брокер сообщений Kafka, указанные в варианте задания, на данном этапе не подключены. Хранение данных реализовано в памяти, чтобы в дальнейшем можно было заменить инфраструктуру хранения без существенного изменения бизнес-логики.

## Архитектура приложения

Решение разделено на отдельные проекты, каждый из которых отвечает за свою часть приложения.

| Проект | Назначение |
|---|---|
| `FitnessClub.Domain` | Сущности предметной области, перечисления и интерфейсы репозиториев |
| `FitnessClub.Contracts` | DTO и интерфейсы прикладных сервисов |
| `FitnessClub.Application` | Бизнес-логика, прикладные сервисы, преобразование сущностей в DTO и аналитические запросы |
| `FitnessClub.Infrastructure.InMemory` | Реализация репозиториев и хранение данных в коллекциях в памяти |
| `FitnessClub.Api` | REST API, контроллеры, обработка HTTP-запросов и регистрация зависимостей |
| `FitnessClub.AppHost` | Оркестрация и запуск приложения с помощью .NET Aspire |
| `FitnessClub.Tests` | Модульные тесты предметной области и запросов |

### Основные принципы реализации

- **Разделение ответственности.** Контроллеры принимают HTTP-запросы и вызывают прикладные сервисы, а бизнес-логика находится в проекте `FitnessClub.Application`.
- **Repository Pattern.** Работа с данными выполняется через интерфейсы репозиториев. Их реализации находятся в инфраструктурном проекте.
- **DTO.** Для передачи данных между клиентом и API используются отдельные объекты передачи данных. Это позволяет не возвращать сущности предметной области напрямую.
- **Dependency Injection.** Сервисы и репозитории регистрируются в контейнере зависимостей и передаются через конструкторы.
- **Асинхронность.** Методы сервисов и репозиториев используют `Task` и асинхронные операции.
- **Валидация.** DTO создания и обновления содержат атрибуты проверки входных данных, например `Required`, `Phone` и `Range`.
- **HTTP-статусы.** Контроллеры возвращают соответствующие коды ответа, включая `200 OK`, `201 Created`, `204 No Content`, `400 Bad Request` и `404 Not Found`.
- **Логирование.** Для регистрации основных операций контроллеры используют `ILogger`.
- **XML-документация.** Публичные методы контроллеров снабжены XML-комментариями.

## Хранение данных

Для лабораторной работы используется реализация `Infrastructure.InMemory`. Начальные тестовые данные добавляются в хранилище при инициализации приложения.

Данные хранятся в оперативной памяти и сбрасываются при повторном запуске приложения. Такая реализация предназначена для проверки REST API и бизнес-логики без подключения внешней базы данных.

Архитектура предусматривает возможность последующей замены реализации репозиториев на работу с базой данных в отдельном инфраструктурном проекте.
